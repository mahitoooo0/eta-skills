用户要求做一次**复盘（retrospective）**。你要针对编码代理的**环境**提出改进建议，让未来的运行更好。

## 步骤

1. 读取本轮的输入来源：**`MEMORY.md`** 与**当前 workspace 里的文件**（规格、计划、任务状态、代码改动、验证记录等）。

   Eta 没有可读的会话日志接口——不要尝试去搜索或读取"会话日志 / 会话记录"，也不要凭回忆编造一次会话的经过。如果用户点名了某段历史，就基于 MEMORY.md 与当前 workspace 里留存的文件来重建；重建不出来就直接说明缺哪些材料。

2. 在下列类别里找改进候选。

- **导航（Navigation）**：代理找对文件有多容易？文件之间有没有隐藏依赖？一个**导航指针**会不会让它更容易？_适用范围_：会话里找某条信息花了很长时间。
- **自动化检查（Automated checks）**：有没有能抓到代理所犯错误的自动化检查？lint、类型检查、测试、文件系统 linter？先读仓库自带的检查命令（它的 `package.json`/构建工具里的 `lint`/`check` 脚本），这样"某个检查其实已存在、只是没接上或悄悄坏了"才是发现，而不是重新发明一遍。一个**没有任何护栏**的仓库——即没有任何自动化 lint/类型检查/测试在每次 implementation 子代理交回后被运行——本身就是一条发现：一个没被 lint 的仓库是持续错过的机会，不是中性的默认。_适用范围_：代理犯了一个本可被自动化检查抓到的错误，或仓库压根没有护栏。

  > Eta 说明：Eta 没有 hook、也没有 CI。这里唯一的落点是——**每次 implementation 子代理交回后，由主代理用 terminal 执行仓库自带的 lint/类型检查/测试命令**。把检查接上的做法就是写清让主代理跑哪条命令。
- **编码标准（Coding standards）**：要不要给 **review 子代理**一条新规则去执行？某条现有规则该删还是该澄清？先给违规分类：**机械性**违规（固定的语法模式、被禁用的 API、导入形态、文件位置规则）就该得到一个确定性检查——在仓库自己的 linter 里加一条自定义规则，或者干脆把它变成主代理每次交回后跑的一条命令，选仓库语言和现有护栏下最省的那种。宁可建立检查，也不要写规则。把 `CODING_STANDARDS.md` 留给真正需要**判断**的场合（跨文件一致性、"符合周边风格"、任何护栏永远无法替代的东西）。_适用范围_：review 子代理没能抓到某个错误。
- **全局 MEMORY.md**：有没有本该被移到编码标准（或自动化检查）里的 steering 指令？_适用范围_：MEMORY.md 特别大——无论在仓库里还是在用户的全局范围。
- **工具经济（Tool economy）**：代理有没有做出本可精简的昂贵工具调用？有没有特别耗 token 的自定义工具链（CLI 调用等）？_适用范围_：代理做了一次昂贵的工具调用。
- **无操作（No-ops）**：在 steering 文件里找出并不改变代理行为的指令。_适用范围_：steering 文件又大又臃肿。
- **信息获取（Information access）**：找出增加代理获取信息渠道的机会。把构建/测试日志留存成代理可读的文件，或开放当前 workspace 里已有材料的只读访问；**不要为此新增任何外部服务**。_适用范围_：有一条关键信息代理拿不到。

3. 把这些候选按严重程度排序，呈现给用户。

## 参考

### 实现 vs 审查（Implementation vs Review）

记住，所有工作都经过两个阶段：implementation 与 review。**implementation 子代理**的上下文压力最大——它负责探索、写代码、调试失败。

**review 子代理**的上下文压力最小——它拿到的是 diff，不需要探索，通常也不需要写代码或调试。

这意味着：施加编码标准应该由 **review 子代理**负责，而不是 implementation 子代理。

### 文件

在仓库里你可以利用以下几类文件：

- `MEMORY.md`：这些内容会进入在本仓库工作的代理的上下文窗口。要极其克制地使用，通常只用来做指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：这份文件在审查阶段读，实现阶段不读（**仅在当前 workspace 实际存在时读，不存在就跳过**）。如果标准文件超过 1,000 行，就给它加**导航指针**指向 docs 目录。
- Docs：把 docs 当作被其他文件指向的参考资料。写新文档前先找找有没有现成的。
- Skills：用技能来承载文档（技能 description 会进入代理的上下文窗口），或承载由用户调用的命令。如果 Eta 技能索引里确实存在写作类技能，就遵循它的写作建议；没有就按本技能正文的风格要求（**不要凭名字假设某个技能已安装**）。
