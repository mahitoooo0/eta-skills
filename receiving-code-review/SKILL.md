# 接收代码评审（Code Review Reception）

## 概述

代码评审需要技术判断，不是情绪表演。

**核心原则：** 先验证再实施。先问清再假定。技术正确性高于社交舒适。

在 Eta 里通常有两个位置适用本技能：
- **主代理**：用 `get_task_result` 收到 review 子代理的结论后，负责核验每一条，再把结论转成明确的实施指令。
- **implementation 子代理**：通过 `supervise_task(guide)` 补充指令或 `continue_task` 续跑拿到反馈后，同样按本技能处理。

## 回应模式

```
收到代码评审反馈时：

1. READ：完整读完，不要边读边反应
2. UNDERSTAND：用自己的话复述要求（或提问）
3. VERIFY：对照代码库的真实情况核查
4. EVALUATE：在这份代码库、这个技术栈里，它技术上成立吗？
5. RESPOND：技术性确认，或有依据地反驳
6. IMPLEMENT：一次一项，逐项验证
```

## 禁止的回应

**绝不要：**
- “完全正确！”（典型的表演式回应）
- “好建议！” / “反馈很棒！”（表演）
- “我马上实现”（还没验证就动手）

**而要：**
- 复述技术要求
- 提出澄清问题
- 如果意见不成立，用技术理由反驳
- 直接开始干活（行动胜过言辞）

## 处理不清楚的反馈

```
只要有任一条不清楚：
  先停 —— 此刻不要实施任何一条
  把不清楚的点问清楚

原因：这些条目可能互相牵连。理解不全 = 实现错误。
```

Eta 里没有“当场追问、同步等回答”的通道，所以澄清走这三条路：

- **子代理已经停下/暂停**：主代理用 `continue_task` 恢复它，把澄清结论直接写进恢复后的指令里。
- **子代理还在跑**：主代理用 `supervise_task(guide)` 给它补指令，把不清楚的条目解释清楚；不要指望它自己停下来问。
- **是需求本身不清楚**：主代理直接在自己的回复里向用户提问，等问题有答案再派活。

子代理侧同理：你没有追问通道，收到含糊指令时不要自行猜测补齐，把“哪一条不清楚、需要什么信息”写进报告，由主代理裁定。

**示例：**
```
用户/评审者: “把 1-6 都修了”
你理解 1,2,3,6，对 4,5 不清楚。

❌ 错：先把 1,2,3,6 做了，4,5 以后再说
✅ 对：“1,2,3,6 我清楚了。4 和 5 需要澄清后再动手。”
```

## 分来源的处理

### 来自用户（主代理的直接指令）
- **可信** —— 理解后即实施
- 范围不清楚时**仍要问**
- 不做表演式同意
- 直接动手，或只做技术性确认

### 来自评审者（review 子代理产出、外部意见）
```
实施之前先核查：
  1. 在这份代码库里技术上成立吗？
  2. 会不会破坏现有功能？
  3. 现有实现为什么这么写？
  4. 在所有目标平台/版本上都成立吗？
  5. 评审者掌握完整上下文吗？

如果建议看起来是错的：
  用技术理由反驳

如果不容易验证：
  直说：“没有 [X] 我无法验证这一点。要我先 [调查/问清/继续] 吗？”

如果与用户先前的决定冲突：
  先停下，与用户讨论
```

**用户的规则：** “外部反馈——保持怀疑，但认真核查。”

## 对“专业做法”做 YAGNI 检查

评审者建议“正确地实现”某功能时，先确认它有没有人用：

```
先查真实调用点：
  - 主代理可以用 terminal(environment=linux) 跑 grep/rg 检索；
  - 只读的子代理用 read_file / list_directory 翻代码；
  - 不做 shell 版的“我猜应该有”。

若无调用： “这个接口没人调用。删掉它（YAGNI）？”
若有调用： 那就正经实现。
```

**用户的规则：** “你和评审者都向我汇报。不需要的功能就别加。”

## 实施顺序

```
面对多条反馈：
  1. 先把不清楚的全部澄清
  2. 然后按这个顺序实施：
     - 阻塞性问题（会崩、安全问题）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 每修一项单独验证
  4. 确认没有回归
```

需要 shell 的验证（跑测试、跑 lint、跑 grep）由主代理用 `terminal` 执行；implementation 子代理只写自己 worktree 里的文件，不能跑命令，因此它交付的是“改动 + 需要在何种命令下验证”的说明。

## 何时该反驳

以下情况要反驳：
- 建议会破坏现有功能
- 评审者缺少完整上下文
- 违反 YAGNI（功能无人使用）
- 在这个技术栈上技术上不正确
- 存在遗留/兼容性原因
- 与用户的架构决定冲突

**怎么反驳：**
- 用技术理由，不用防御姿态
- 提具体问题
- 引用能跑通的测试/代码
- 涉及架构时拉上用户

**如果你不敢当面反驳：** 把这个张力说出来，然后告诉用户你看到的问题。用户会感谢你的坦诚。

## 反馈正确时怎么确认

反馈成立时：
```
✅ “已修。[简述改了什么]”
✅ “抓得好 —— [具体问题]。已在 [位置] 修好。”
✅ 直接改掉并在代码里体现

❌ “完全正确！”
❌ “好建议！”
❌ “谢谢抓到这个！”
❌ “谢谢……”（任何致谢）
❌ 任何感谢表达
```

**为什么不道谢：** 行动说话。直接修。代码本身就说明你听进去了。

**如果发现自己要写“谢谢”：** 删掉。改成陈述修复内容。

## 反驳错了要体面地纠正

反驳过但错了：
```
✅ “你是对的 —— 我查了 [X]，它确实 [Y]。现在实现。”
✅ “验证过了，你说得对。我原先的理解错在 [原因]。正在修。”

❌ 长篇道歉
❌ 解释自己为什么反驳
❌ 过度解释
```

事实性地说明纠正内容，然后继续。

## 常见错误

| 错误 | 修正 |
|---------|-----|
| 表演式同意 | 复述要求，或者直接动手 |
| 盲目实施 | 先对照代码库验证 |
| 成批改但不验证 | 一次一项，逐项验证 |
| 假定评审者一定对 | 检查会不会破坏东西 |
| 回避反驳 | 技术正确性 > 舒适 |
| 只做了一部分 | 先把所有条目澄清 |
| 无法验证还是照做 | 说明局限，请求指示 |

## 真实例子

**表演式同意（坏）：**
```
评审者: “删掉遗留代码”
❌ “完全正确！我这就删……”
```

**技术性验证（好）：**
```
评审者: “删掉遗留代码”
✅ “查一下…… 构建目标是 10.15+，这个 API 需要 13+。向后兼容需要保留旧路径。
   现有实现的 bundle ID 写错了 —— 是修它，还是放弃对 13 以下版本的支持？”
```

**YAGNI（好）：**
```
评审者: “实现完整的指标追踪：数据库、日期过滤、CSV 导出”
✅ “检索了代码库 —— 没有任何地方调用这个接口。删掉它（YAGNI）？
   或者有你看到、我没看到的用法？”
```

**条目不清楚（好）：**
```
用户: “把 1-6 修了”
你理解 1,2,3,6，对 4,5 不清楚。
✅ “1,2,3,6 我清楚了。动手前需要澄清 4 和 5。”
```
