# Systematic Debugging（系统化调试）

## Overview（概述）

**核心原则：** 永远先找到根因，再尝试修复。修症状就是失败。

**违反这个流程的字面，就是违反调试的精神。**

## The Iron Law（铁律）

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
没有根因调查，就没有修复
```

如果你没有完成 Phase 1，就不能提出修复。

## 平台前提（Eta）

- 命令执行（复现、跑测试、`git diff` / `git log`、日志采集等）由**主代理**用 `terminal(environment=linux)` 执行；子代理不能执行 shell、GUI、浏览器。
- 子代理只做只读分析与推理（`read_file` / `list_directory`）。需要复现或采集证据时，请主代理跑命令并把输出粘贴给你，你基于输出推理；不要提出"自己去跑一下"这类依赖 shell 的步骤。
- 需要补充信息或调整方向时，让主代理知道（它可以用 `supervise_task(guide)` 给运行中的子代理补指令，或用 `continue_task` 恢复暂停的任务）。

## When to Use（何时使用）

适用于任何技术问题：
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在这些时候使用：**
- 有时间压力（紧急情况让猜测变得诱人）
- "就一个快速修复"看起来很明显
- 你已经试过多个修复
- 上一个修复没用
- 你还没有完全理解问题

**不要在这些时候跳过：**
- 问题看起来简单（简单 bug 也有根因）
- 你赶时间（赶时间保证返工）
- 用户/主代理要求立刻修复（系统化比反复折腾更快）

## The Four Phases（四个阶段）

你必须完成每个阶段，才能进入下一个。

### Phase 1: Root Cause Investigation（根因调查）

**在尝试任何修复之前：**

1. **仔细读错误信息**
   - 不要跳过错误或警告
   - 它们常常包含确切的解法
   - 完整读栈追踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 能可靠触发吗？
   - 确切步骤是什么？
   - 每次都发生吗？
   - 如果不能复现 → 收集更多数据，不要猜
   - （复现命令由主代理执行，输出粘贴给你；你基于输出判断能否稳定复现。）

3. **检查最近的改动**
   - 什么改动可能导致这个？
   - `git diff`、最近的提交
   - 新依赖、配置变更
   - 环境差异
   - （由主代理用 `terminal` 跑 `git diff` / `git log` 并把输出给你。）

4. **在多组件系统里采集证据**

   **当系统有多个组件时（CI → 构建 → 打包，API → 服务 → 数据库）：**

   **在提出修复之前，加入诊断埋点：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传递
     - 检查每一层的状态

   跑一次，采集显示"在哪里断"的证据
   然后分析证据，找出出问题的组件
   然后调查那个具体组件
   ```

   **示例（多层系统）：**
   ```
   # Layer 1: 工作流
   echo "=== 工作流中可见的 Secrets: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: 构建脚本
   echo "=== 构建脚本中的环境变量: ==="
   env | grep IDENTITY || echo "IDENTITY 不在环境里"

   # Layer 3: 运行环境
   echo "=== 运行环境中的关键配置: ==="
   env | grep APP_ || echo "没有 APP_ 前缀的配置"

   # Layer 4: 实际运行入口
   echo "=== 实际运行时拿到的参数: ==="
   echo "ENTRY: ${ENTRY:-UNSET}"
   ```
   （这些诊断命令由主代理用 `terminal` 执行。）

   **这能揭示：** 哪一层失败（secrets → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误在调用栈深处时：**

   完整的前向回溯技巧见本目录下的 `root-cause-tracing.md`。

   **快速版：**
   - 坏值从哪来？
   - 谁用坏值调用了这里？
   - 一直往上追到源头
   - 在源头修，不在症状处修

### Phase 2: Pattern Analysis（模式分析）

**先找模式，再修复：**

1. **找可用的范例**
   - 在同一代码库里找相似的可运行代码
   - 有什么和坏掉的东西相似、但是好的？

2. **对照参考实现**
   - 如果要实现某个模式，完整读参考实现
   - 不要略读 —— 每一行都读
   - 在套用之前完整理解该模式

3. **找出差异**
   - 好的和坏的之间差在哪？
   - 列出每一处差异，无论多小
   - 不要假设"那个不可能有关系"

4. **理解依赖**
   - 它还需要哪些其它组件？
   - 哪些设置、配置、环境？
   - 它做了哪些假设？

### Phase 3: Hypothesis and Testing（假设与测试）

**科学方法：**

1. **形成单一假设**
   - 明确陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化测试**
   - 做尽可能小的改动来检验假设
   - 一次一个变量
   - 不要一次修多件事

3. **继续前先验证**
   - 成了吗？是 → Phase 4
   - 没成？形成新假设
   - 不要在旧修复之上再堆修复

4. **当你不知道时**
   - 说 "I don't understand X"
   - 不要假装知道
   - 让主代理知道（它可以用 `supervise_task(guide)` 补指令，或直接问用户）
   - 做更多研究

### Phase 4: Implementation（实现）

**修根因，不修症状：**

1. **创建失败测试用例**
   - 尽可能简单的复现
   - 尽量做成自动化测试
   - 没有框架就写一次性测试脚本
   - 修复前必须有
   - 用红-绿循环确认这个测试确实先失败、修复后再通过

2. **实现单一修复**
   - 针对已识别的根因
   - 一次一处改动
   - 不要"顺手"改进
   - 不要捆绑重构

3. **验证修复**
   - 现在测试通过了吗？
   - 没有破坏其它测试吗？
   - 问题真的解决了吗？
   - 在宣称成功之前，由主代理按本目录下的兄弟技能 verification-before-completion 的检查项执行验证

4. **如果修复没用**
   - 停下
   - 计数：你试了几个修复？
   - 若 < 3：回到 Phase 1，用新信息重新分析
   - **若 ≥ 3：停下，质疑架构（见下面第 5 步）**
   - 没有架构层面的讨论，不要尝试第 4 个修复

5. **若 3 个以上修复失败：质疑架构**

   **表明架构有问题的模式：**
   - 每个修复都在不同地方暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每个修复在别处制造新症状

   **停下，质疑根本假设：**
   - 这个模式根本上是合理的吗？
   - 我们是不是"纯粹靠惯性在坚持"？
   - 该重构架构，还是继续修症状？

   **在尝试更多修复前：停下继续改，把架构疑点报告给主代理，由主代理决定是否与用户讨论后续方案**

   这不是一个失败的假设 —— 这是一个错误的架构。

## Red Flags - STOP and Follow Process（危险信号 —— 停下并走流程）

如果你发现自己这样想：
- "先快速修一下，以后再查"
- "就试试改 X，看看行不行"
- "加多处改动，跑测试"
- "跳过测试，我手动验证"
- "大概是 X，我来修一下"
- "我没完全理解，但这个也许能用"
- "模式说的是 X，但我换个方式套"
- "主要问题有这些：[不调查就列修复]"
- 追踪数据流之前就提出方案
- **"再试一个修复"（已经试了 2 个以上时）**
- **每个修复都在不同地方暴露新问题**

**所有这些都意味着：停下。回到 Phase 1。**

**若 3 个以上修复失败：** 质疑架构（见 Phase 4.5）

## 用户的信号：你在做错

**留意这些纠偏：**
- "难道不是没有发生吗？" —— 你没验证就假设了
- "这能让我们看到……吗？" —— 你本该加入证据采集
- "别猜了" —— 你在不理解的情况下提修复
- "深入想想这个" —— 质疑根本假设，不只是症状
- "我们卡住了？"（烦躁）—— 你的方法不奏效

**看到这些时：** 停下。回到 Phase 1。

## Common Rationalizations（常见合理化）

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要流程" | 简单问题也有根因。对简单 bug，流程很快。 |
| "紧急，没时间走流程" | 系统化调试比猜-验反复折腾更快。 |
| "先试这个，再调查" | 第一个修复定下基调。从一开始就做对。 |
| "我确认修复有效后再写测试" | 没测过的修复不会持久。先写测试才能证明。 |
| "一次修多处省时间" | 无法隔离出哪个起了作用。会引入新 bug。 |
| "参考太长了，我照着套一下模式" | 部分理解必然出 bug。完整读完。 |
| "我看到问题了，让我来修" | 看到症状 ≠ 理解根因。 |
| "再试一个修复"（失败 2 次以上后） | 失败 3 次以上 = 架构问题。质疑模式，别再修。 |

## Quick Reference（速查）

| 阶段 | 关键活动 | 成功判据 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、检查改动、采集证据 | 理解 WHAT 和 WHY |
| **2. 模式** | 找可用范例、对照 | 找出差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或形成新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## When Process Reveals "No Root Cause"（当流程揭示"没有根因"）

如果系统化调查揭示问题确实是环境性的、时序相关的或外部的：

1. 你已经走完了流程
2. 记录你调查了什么
3. 实现适当的处理（重试、超时、错误信息）
4. 为将来的调查加入监控/日志

**但是：** 95% 的"没有根因"案例是调查不完整。
